### Revision identifiers and load confirmation

Three different values identify a snapshot. They must not be confused:

| Name | Example (development snapshot) | Where it comes from | Used for |
| --- | --- | --- | --- |
| Short revision | `9bb3b26` | First 7 hex digits of the git commit; appears only in the directory name `IDX-Dataset-9bb3b26` | Human reference only. **Never accepted** for confirmation |
| Source revision (full) | `9bb3b26bd28ab46bc2f3e74a7c03805ce053301b` | `manifest.json` → `revision`; stored as `source_snapshots.source_revision` | The **only** value accepted by `--confirm-revision` / `confirm_revision=` |
| `snapshot_id` | `pholenk-idx-dataset:9bb3b26bd28ab46bc2f3e74a7c03805ce053301b:<first 16 hex of content_sha256>` | Derived: source id + full revision + content hash (§1) | Deterministic database identity; computed, never typed by the operator |

**Load confirmation.** A database load requires `--execute` together with
`--confirm-revision <full 40-hex manifest revision>`. The value must be
**exactly equal** to the manifest's `revision`: no prefix, short SHA, or
case-insensitive match is accepted. On a mismatch, the CLI exits with status 2
before creating a database engine. `SnapshotLoader.load` repeats the check
itself and raises `LoadNotConfirmedError` before any database access.

Confirmation proves that the operator named the intended source revision. It
does not pin the file contents; that is what `content_sha256` in the
`snapshot_id` and the pass-2 hash re-check do. The dry-run report prints
`source_revision`, `content_sha256`, and `snapshot_id`, so the operator
can review them before confirming.

Get-or-create: look up by (`source_id`, `source_revision`, `content_sha256`).
If it exists, every registered `source_files.sha256` must equal the
recomputed hash (it will, since the content hash matches). If the same
`source_id` + `source_revision` exists with a **different** `content_sha256`,
a new snapshot is registered and a `snapshot_content_mismatch` incident
(severity `error`) is recorded in the run.

## 2. File inventory

**Scope:** every file under `raw_storage_path` except `manifest.json`, which is
our retrieval metadata and contains `retrieved_at`. Hashing the whole
extracted content means that loading more of the snapshot later (e.g. index
files) never changes its identity.

The loader reads the snapshot in **two passes**. This is intentional, and each
stock file is therefore read twice (once per pass). The invariant is:

> For each parsing pass, hashing and parsing use the same bytes. The second
> pass re-hashes the file before parsing and fails if the file changed.

Memory stays bounded: at most one file's bytes are held at a time, and the
dataset is never materialized in memory.

Procedure (**pass 1**, no parsing of prices yet):

1. Enumerate files recursively; sort by `relative_path`.
2. For each file: read its bytes, compute SHA-256 from those bytes, and
   record `relative_path`, `sha256`, and size. The bytes are released before
   the next file is read.
3. For stock files (`dataset/stocks/csv/*.csv`): from the **same bytes**,
   decode UTF-8 (BOM allowed), check the header against the 26 verified
   columns, count data rows (`row_count`), and capture per file: `source_key`
   (file stem), the newest row's `Name`, the newest `Date`, and whether any
   `Ticker` cell differs from the key.
4. Other files get `row_count` = data rows for CSVs (header excluded) or `0`
   for non-CSV files, and `source_key = NULL`.

Structural checks, all **fatal**. In pass 1 they happen before any database
access, so nothing is written:

| Check | Failure |
| --- | --- |
| `dataset/stocks/csv/` exists | missing directory |
| Every stock file name matches `^[A-Z0-9]+\.csv$` | unexpected file (e.g. `True.csv`, `x.txt`) |
| No subdirectories inside `dataset/stocks/csv/` | unexpected layout |
| Stock header equals the verified 26 columns | schema drift |
| UTF-8 decodes | encoding drift |
| Optional `--expect-stock-files N` matches | missing/extra files vs operator expectation |

Pass-1 failures happen before any database access, so nothing is written (not
even a run record).

**Pass 2** (the dry run or the load) reads each stock file's bytes again, one
file at a time, and re-computes SHA-256 from those bytes. If the hash differs
from pass 1, it raises a structural error. During a load, that **fails the
run**: T1 is rolled back, and only the T0 registration plus the `failed` run
remain. Otherwise rows are parsed from those same second-pass bytes. The
bytes parsed are therefore provably the bytes hashed and registered, without
holding the whole snapshot in memory.

`source_files` rows: one per inventoried file (1,043), inserted with
`ON CONFLICT (snapshot_id, relative_path) DO NOTHING`, then read back to map
`relative_path → file_id`.

## 3. Security resolution

For each stock file, in sorted `source_key` order (this makes `security_id`
assignment deterministic on an empty database):

1. Look up `security_source_keys (source_id, source_key)`.
2. If absent: insert `securities` (`ticker = source_key`,
   `name = newest-row Name`, `currency = 'IDR'`,
   `identity_kind = 'development'`), then insert the mapping with
   `first_seen_snapshot_id = this snapshot`.
3. If present: reuse its `security_id`. Display metadata is updated only when
   the incoming file's newest `trading_date` is **later** than the latest
   `trading_date` already stored for that security. Then `name` = the newest
   row's `Name`; `ticker` stays the source key. Loading an older snapshot
   after a newer one therefore never regresses the display name. Name history
   is not recorded (deferred).

Rules:

* The **file key is the source key**; the `Ticker` column is never used as
  identity. Ticker is never a permanent identity.
* Distinct source keys are distinct securities. There is **no** matching by
  name or ticker text, and no merging.
* **`TRUE.csv`:** key `TRUE`. Its `Ticker` column reads `True` (case-only
  difference, accepted as in Phase 2A). The mapping gets the flag
  `source_ticker_column_mismatch`, and one incident records the raw value
  (§5). Any non-case mismatch is a row-level hard-invalid record (§6).

## 4. Row normalization

Pass 2 streams each stock file one row at a time (source order does not matter;
the key is security + date):

| Raw field | `daily_prices` column | Rule |
| --- | --- | --- |
| `Date` | `trading_date` | `YYYY-MM-DD` → DATE (exchange-local). Malformed → hard-invalid row |
| file key | `security_id` | Via §3 |
| — | `source_id` | `pholenk-idx-dataset` |
| `Open` | `open` | `0` → NULL; never filled from close, reference price, a previous open, or forward fill |
| `High`, `Low` | `high`, `low` | `0` → NULL (the zero-volume placeholder). A `traded` row with NULL high/low is hard-invalid |
| `Close` | `close` | Source value unchanged (on zero-volume rows it is the reference/carried price) |
| `Previous` | `reference_price` | Source value; `0` → NULL. **Not** "previous close" |
| `Volume` | `volume` | Integer shares, **regular market** |
| `Value` | `value` | Exact decimal IDR, **regular market** |
| `Frequency` | `frequency` | Integer, **regular market** |
| `NonRegularVolume` | — | Not stored; drives the flag in §5; stays in the raw file |
| `Name`, `Ticker`, `Remarks`, other columns | — | Not stored per row; raw file keeps them |
| — | `trading_status` | `traded` if `volume > 0`; `no_regular_market_trade` if `volume = 0` and raw `High = Low = 0`; otherwise `unknown` |
| — | `quality_flags` | §5; stored **sorted and de-duplicated** |
| — | `file_id`, `source_line` | Provenance (§10) |
| — | `ingestion_run_id` | The current run (used only when the row is inserted) |

No price adjustment, no return calculation, and no derived fields are
computed.

**Validation parity:** the loader's row validation must reject everything the
database CHECK constraints reject (positivity, status vocabulary,
`traded_shape`, `no_regular_trade_shape`, flag vocabulary). A CHECK violation
during the insert means the two disagree: it aborts the transaction and fails
the run. It is a bug to fix, never data to skip.

## 6. Hard-invalid vs quarantine behaviour

| Situation | Scope of effect | Incident | Counters |
| --- | --- | --- | --- |
| Row fails parsing (bad date/number, wrong field count) or hard validation (e.g. `high < low` on a traded row, negative volume, non-positive price, non-case ticker mismatch) | **Row quarantined**: not inserted; the rest of the file continues | `hard_invalid_record`, `error`, with `file_id`, `source_line`, raw cells, issue codes | `rows_rejected` |
| Two rows with the same (key, date) in one snapshot, **identical** content | Keep the lowest `source_line`; drop the other | none | `rows_collapsed_duplicates` (in `validation_summary.counters`) |
| Two rows with the same (key, date) in one snapshot, **different** content | **Whole security batch rejected** for this run: none of that key's rows are inserted | `conflicting_duplicate_in_snapshot`, `error`, with all involved lines | all rows of that key → `rows_rejected` |
| Incoming row differs from the stored row (same key) | **Stored row preserved**; incoming not written | `conflicting_observation`, `error` (§9) | `rows_conflicted` |
| Incoming row identical to the stored row | No-op | none | `rows_unchanged` |
| Structural file/snapshot problem (§2 checks, pass-2 hash change, unreadable file) | **Run fails**; no canonical writes | none (the run's `validation_summary.error` holds the cause) | — |
| Database CHECK violation during insert | **Run fails** (validation-parity bug) | none | — |

Counter invariant for a successful run:

`rows_seen = rows_inserted + rows_unchanged + rows_rejected + rows_conflicted + rows_collapsed_duplicates`

where `rows_seen` counts raw data rows in the stock files.

## 7. Ingestion run lifecycle

Schema states: `running` → `succeeded` | `failed`. No other transitions.
A retry is a **new** run; a finished run is never reopened.

Connections and transactions:

1. **Lock.** Take a session-level advisory lock for the source
   (`pg_advisory_lock(<int8 hash of source_id>)`) on the loader's connection,
   held until the end. A concurrent loader for the same source waits or fails
   fast (`pg_try_advisory_lock`).
2. **T0 — registration (committed on its own).** Upsert `data_sources`;
   get-or-create `source_snapshots`; insert `source_files`; insert
   `ingestion_runs` (`status = 'running'`, `started_at = now()`,
   `parser_version`). A snapshot-content-mismatch incident is also written
   here. Committing first means a later failure can always be recorded
   against an existing run.
3. **T1 — load (single transaction).** Security resolution (§3), key flags
   and their incidents, staging COPY (§11), classification, inserts of new
   observations, all other incidents, and finally `UPDATE ingestion_runs SET
   status='succeeded', completed_at=now(), counts…, validation_summary=…`.
   Commit.
4. **On any exception in T1:** roll back T1 entirely, then in a new
   transaction `UPDATE ingestion_runs SET status='failed', completed_at=now(),
   validation_summary = {"error": …, "phase": …}`.
5. Release the advisory lock.

**A failed run leaves no partial canonical data:** no `daily_prices`, no new
`securities` or mappings, and no incidents from T1. What remains is the
registration from T0 (snapshot, files, run marked `failed`). That is
accurate, immutable evidence and is reused by the retry.

## 8. Idempotency

| Case | Outcome |
| --- | --- |
| Same snapshot loaded twice | Same `snapshot_id` (content-derived); new run; `rows_inserted = 0`, `rows_unchanged = rows_seen − rejected − collapsed`, `rows_conflicted = 0`; no new incidents |
| Same snapshot, same parser version | As above; results identical |
| Same snapshot, **different** parser version whose output differs | Differing rows become `conflicting_observation` incidents; stored rows untouched (applying them is a future correction workflow) |
| Same (source, security, date) observation from a different snapshot, identical values | `rows_unchanged`; provenance stays first-seen |
| Different source revision | New snapshot (different `snapshot_id`); rows compared as above |
| Same revision, changed file content | Different `content_sha256` → new snapshot + `snapshot_content_mismatch` incident; rows compared as above |
| Incoming value differs from stored value | Stored row kept; `conflicting_observation` incident with both versions |

Incident de-duplication: before inserting an incident, the loader checks for
an existing incident with the same `incident_type` and the same subject: for
row incidents (`source_id`, `security_id`, `trading_date`) plus identical
`details.incoming`; for key incidents (`source_id`, `security_id`). If one
exists, none is added. A clean identical rerun therefore records **zero**
incidents.

## 9. Conflict detection

`ON CONFLICT DO NOTHING` is only a safety net; it cannot tell identical from
conflicting. Classification happens **before** inserting, by comparing
incoming (staging) rows with stored rows on the full key
(`security_id`, `trading_date`, `source_id`):

* **Compared (the observation):** `open`, `high`, `low`, `close`,
  `reference_price`, `volume`, `value`, `frequency`, `trading_status`,
  `quality_flags`.
* **Not compared (provenance):** `file_id`, `source_line`, `ingestion_run_id`.
  They legitimately differ between snapshots.

```sql
-- per staging row: new / unchanged / conflict
SELECT s.*,
       CASE
         WHEN d.security_id IS NULL THEN 'new'
         WHEN (d.open, d.high, d.low, d.close, d.reference_price,
               d.volume, d.value, d.frequency, d.trading_status, d.quality_flags)
              IS NOT DISTINCT FROM
              (s.open, s.high, s.low, s.close, s.reference_price,
               s.volume, s.value, s.frequency, s.trading_status, s.quality_flags)
           THEN 'unchanged'
         ELSE 'conflict'
       END AS outcome
FROM stage s
LEFT JOIN daily_prices d
  ON (d.security_id, d.trading_date, d.source_id)
   = (s.security_id, s.trading_date, s.source_id);
```

* `IS [NOT] DISTINCT FROM` is NULL-safe (two NULL opens are equal).
* NUMERIC compares by value (`5975.0` = `5975.0000`).
* `quality_flags` compare equal because both sides are stored sorted and
  de-duplicated.
* New rows are inserted with `INSERT … SELECT … WHERE outcome = 'new'`
  (`ON CONFLICT DO NOTHING` kept as a guard). The inserted row count must
  equal the classified `new` count, otherwise the run fails. The advisory lock
  makes a mismatch impossible under correct operation.
* Conflict incidents: `details = {"stored": {…observation…}, "incoming":
  {…observation…}, "stored_provenance": {"file_id", "source_line",
  "ingestion_run_id"}, "incoming_provenance": {"file_id", "source_line"}}`,
  with `file_id` / `source_line` columns pointing at the incoming raw row.

## 10. Provenance

Every `daily_prices` row reproduces as:

```text
daily_prices.file_id ──> source_files (relative_path, sha256, row_count, source_key)
                              └──> source_snapshots (source_revision, content_sha256,
                                   archive_sha256, source_url, retrieved_at,
                                   licence_reference, raw_storage_path)
daily_prices.source_line  (physical CSV line; header = line 1)
daily_prices.ingestion_run_id ──> ingestion_runs (parser_version, started_at)
```

To reproduce: open `raw_storage_path/relative_path`, verify `sha256`, read
`source_line`, and re-apply `parser_version`. Provenance is **first-seen**:
unchanged observations keep the file, line, and run that inserted them.

## 11. Transactions and performance

Target: 1,289,820 rows in one T1 transaction, without holding the dataset in
Python memory.

1. **Staging table** in T1: `CREATE TEMP TABLE stage (…daily_prices
   observation columns…, file_id, source_line) ON COMMIT DROP`. It exists only
   in this transaction and is not part of the schema or migrations.
2. **Streaming COPY:** psycopg 3 `cursor.copy("COPY stage (…) FROM STDIN")`,
   obtained through SQLAlchemy's `Connection.connection.driver_connection`.
   The loader writes one row at a time with `copy.write_row(...)` while
   iterating file by file.
   * Python memory: one file's bytes and rows (≤ 1,537 rows), the inventory
     (1,043 entries), and the key → `security_id` map (983 entries).
   * Within-file duplicate detection runs in memory per file, since each
     security's rows are in one file.
3. **Prepare staging:** `CREATE INDEX ON stage (security_id, trading_date)`,
   then `ANALYZE stage`. Also a defensive
   `SELECT … GROUP BY key HAVING count(*) > 1` that must return nothing.
4. **Classify + insert + incidents** with set-based SQL (§9). No row-by-row
   round trips.
5. **Indexes on `daily_prices` stay in place.** The primary key is needed for
   classification; maintaining `ix_daily_prices_trading_date` at this size is
   cheap.
6. **One transaction** for atomicity (§7). Expected WAL volume is a few
   hundred MB and runtime is on the order of a minute locally; both are
   acceptable. No mid-run commits.
7. `security_id` resolution (983 keys) happens before streaming, using
   pass-1 data. It is one query to fetch existing mappings plus inserts for
   new keys.

## 12. Dry-run mode

The dry run, which is the CLI default (no `--execute`), performs pass 1 and
pass 2 fully (read, hash, parse, normalize, validate, flag, detect duplicates)
with **zero database writes**.

* **Default (offline):** no database connection at all. Identity resolution is
  logical: every key is reported as "would be created", in deterministic
  sorted order.
* **`--compare-db` (optional; not implemented in Phase 2B.3B, deferred):**
  opens a `READ ONLY` transaction. PostgreSQL forbids `CREATE`, even of
  temporary tables, in such a transaction, so no staging table is used. Instead the dry run SELECTs the existing mappings and,
  per security, the stored observations, then applies the §9 comparison rule
  in Python (same compared columns, NULL-safe, numeric by value, flags as
  sorted sets). It reports would-be new / unchanged / conflict counts. The
  offline mode remains the reference output.
* **Report:** deterministic JSON with sorted keys and no wall-clock
  timestamps. Contents:
  * `snapshot_id`, `content_sha256`, `source_revision`, `retrieved_at`
    (from the manifest), `parser_version`;
  * file counts by role (stock / index / preview / other);
  * per stock file: `relative_path`, `sha256`, `row_count`, `source_key`;
  * totals: rows seen, rows that would be inserted, rejected (with reasons),
    collapsed duplicates, rejected security batches;
  * status counts, missing-open count, zero-volume count, flag counts, date
    range, key flags;
  * the list of incidents that would be created.
* Running the dry run twice on the same snapshot and parser version produces
  **byte-identical** reports.

## 15. Failure and recovery

* **Detection:**
  * the run is `failed`, with `validation_summary.error` holding the phase
    and message;
  * or the run is **stale** `running`: its advisory lock is not held by any
    backend (`pg_locks`), meaning the process died between T0 and the end.
* **Stale runs:** an operator marks them failed:
  `UPDATE ingestion_runs SET status='failed', completed_at=now(),
  validation_summary = jsonb_build_object('error','stale: process terminated')
  WHERE ingestion_run_id = :id AND status = 'running'`. The CHECK constraints
  keep this consistent.
* **Safe retry:** fix the cause and run the loader again. It creates a new
  run and reuses the registered snapshot and files. Because T1 is atomic, the
  failed run left no canonical rows, so the retry behaves like a first load.
  Because loading is idempotent (§8), retrying after an unknown outcome is
  safe too.
* **Never** delete registration rows to "clean up": they are evidence, and
  the foreign keys are RESTRICT.

## Implementation prerequisites (Phase 2B.3B)

Items 1–4 were implemented in Phase 2B.3B, except for the parts marked "not
yet built" and a dedicated DB-CHECK parity test. The fixture loads exercise
the CHECK constraints but do not enumerate them. Item 5 remains open.

Changes the loader needs in existing code:

1. **Provider/parser:**
   * parse from supplied bytes, so each pass hashes and parses the same bytes;
   * report row-level parse failures as quarantinable records instead of
     raising for the whole file;
   * expose `NonRegularVolume`, ticker-cell mismatches, and the newest row's
     name/date per file.
2. **Contract renames** (data contract, "Required implementation changes"):
   * `NO_TRADE_OR_SUSPENDED` → `no_regular_market_trade`;
   * `previous_close` → `reference_price`;
   * stop presenting `retrieved_at` as `available_at`;
   * the Phase 2A deterministic run id is replaced by `snapshot_id` plus a
     UUID run.
3. **A loader module and CLI** (dry run by default; `--execute`,
   `--confirm-revision`, `--expect-stock-files`). Not yet built:
   `--compare-db` and the verification command from §13.
4. **Tests on small fixtures and an ephemeral transaction/database:**
   * first load;
   * identical rerun (0 inserted, 0 incidents);
   * a conflicting rerun (incident, stored row unchanged);
   * a quarantined row;
   * a conflicting in-snapshot duplicate rejecting its security;
   * a structural failure leaving no canonical rows and a `failed` run;
   * dry-run determinism;
   * validation parity with the database CHECKs.
5. **Contract text update** reflecting the approved schema refinements
   (parser version on runs).

## Schema gaps

No gap blocks this design; the approved schema supports every behaviour
above. Notes:

1. **No dedicated counter for collapsed exact duplicates.** It is stored in
   `ingestion_runs.validation_summary.counters.rows_collapsed_duplicates`,
   together with the other counters that have no column (incidents, files,
   securities). The counter invariant (§6) uses it.
2. **No explicit file-role column** on `source_files`. The role (stock /
   index / preview / other) is derived from `relative_path`.
3. **No natural uniqueness key on `data_quality_incidents`.** The loader
   de-duplicates by query before inserting (§8). A partial unique index could
   be added later if needed; it is not required now.
4. **`security_source_keys.quality_flags` is cumulative**, not
   snapshot-scoped. Timing and location live in incidents.
5. **`archive_sha256` cannot be re-verified** from the extracted directory. It
   is recorded as download-time provenance, and each run records whether it
   was verified.
